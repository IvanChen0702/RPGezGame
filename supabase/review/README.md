# Supabase 整理前的唯讀檢查

目前狀態：**本對話未直接連線，已收到使用者提供的線上唯讀盤點**。報告確認四項需修正的問題，詳見 [439／440 更新說明](../README.md)；新的 [唯讀部署驗證](verify438_439.sql) 可用來分別檢查專案修正及平台預設授權的實際狀態，未處理的 supabase_admin 授權仍會列出。此對話尚未執行正式變更。以下保留最初盤點工具與檢查方向。

`database_inventory437.sql` 是後續取得管理連線時可執行的唯讀盤點；查詢系統目錄與統計，不讀玩家存檔、帳號內容或私密設定。設有逾時，以唯讀交易執行並回滾。輸出包括表格容量、估計資料量、RLS、授權、索引、重複索引候選、外鍵索引及函式資訊。SQL 已在隔離 PostgreSQL 相容引擎中，以模擬表格、RLS、函式及索引測試；這不代表正式資料庫已驗證。

## 取得連線後的檢查順序

1. 確認專案為 `ynzaotitxntrhubwfinr`，唯讀取得最新 schema、`game-api` 與排程設定，再執行盤點 SQL。盤點結果應存於非公開工作區，不放入網站。
2. 先按容量找主要來源，查看統計重設時間與夠長的觀察區間，再評估索引；`idx_scan = 0` 不等於可以刪除，空表也可能是新功能或低頻資料。
3. 對照前端、當前 Edge Functions、`.gs`、資料庫函式、排程及舊客戶端，建立物件引用清單；函式名稱版本舊或 `pg_depend` 未列出依賴，均不足以判定廢棄。
4. 查核玩家資料的 RLS、函式 EXECUTE 授權、SECURITY DEFINER 的 search_path；只有確定問題後才提出具體修正。
5. 如需清資料，先提供精確的資料表、條件、資料筆數、依賴與回復方案，取得對破壞性操作的確認，再執行。

## 依現有參考程式提出的檢查方向（非線上發現）

| 類別 | 應檢查 | 必須保留的相容性 |
| --- | --- | --- |
| 在線狀態 | 過期 presence 列、帳號／時間查詢的索引與清理排程 | 前端仍有 `game_town_presence420` 相容路徑，不能因新增 436 就刪除 420 |
| 戰鬥與交易回執 | 已結束紀錄的容量、重試期限、清理機制 | `game_battle_status79`、背包、寵物、抽獎依賴回執防止重複領取或扣款 |
| 遺物探險 | 已關閉 run 與未完成 run 的容量 | 保存並離開的探險不能當作過期垃圾；需核對結算與恢復流程 |
| 競技場與世界 BOSS | 歷季快照、已結算且已領取獎勵的歷史資料 | 戰鬥快照、排行榜、尚未領取的獎勵及稽核需求 |
| 企劃版本 | Excel／`.gs` 發布後是否累積舊版本、哪個版本仍被引用 | 戰鬥 snapshot 含 planningVersion；不能只保留最新一份就刪舊版本 |
| 索引與維護 | 重複索引、外鍵前綴索引、dead tuples、autovacuum／analyze 時間 | 主鍵、唯一與約束支援索引，以及低頻結算查詢；不直接執行 VACUUM FULL |
| 玩家資料 | RLS、JSONB 查詢方式與實際慢查詢 | Accounts、PlayerSaves、identity links、裝備及進度不納入自動清理 |

參考來源為 GitHub 前端，以及使用者先前提供的 `game-api-v11.38.411.ts`／Excel；附件版本不等同當前部署版本。Excel 的 `*_SCHEMA` 工作表也不代表線上存在同名資料表。不能據此宣稱某資料表已無用途。
